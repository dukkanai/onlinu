# روابط المطاعم داخل ChatGPT والنطاقات الخاصة

قرار تخطيطي معتمد من المالك في 9 أكتوبر 2026. الحالة: **مخطط وغير منفذ**. يضيف هذا القرار رحلة اكتشاف عامة، ورابطًا لكل مطعم، ونطاقًا خاصًا اختياريًا يحوّل إلى واجهته في ChatGPT. هو جزء من [خطة التحول](SAAS-TRANSFORMATION-PLAN.ar.md)، ولا يغيّر أولوية إصلاحات الأمن والمفاتيح وقبول الدفع وPaylink القائمة.

هذا التحديث وثائق فقط: لا تغيير DNS أو Caddy أو خدمة منشورة، ولا إصدار شهادة أو إنشاء حساب مزود أو توسيع صلاحيات أو تفعيل نطاق. اختيار المزود والتكلفة واسم مضيف التحويل الفعلي وقبول الأجهزة متطلبات تنفيذ لاحقة. يبقى أصل الاختبار الحالي `https://almujeeb.info` كما هو؛ نطاقات المطاعم المستقبلية لا تستبدله.

## 1. القرار ورحلة العميل

- إضافة Onlinu واحدة وبوابة MCP واحدة تخدم المطاعم المنشورة. لا إضافة منفصلة أو مراجعة OpenAI منفصلة لكل مطعم.
- المدخل العام يفتح دليل المطاعم والبحث، ثم يختار العميل مطعمًا. الرابط الخاص يفتح منيو المطعم المقصود مباشرة ضمن الإضافة نفسها، دون الحاجة إلى كتابة اسمه للمساعد. تبقى هوية المطعم ظاهرة عند التصفح والسلة.
- يعتمد الرابط على معرف نشر ثابت أو `public_slug` يحلّه الخادم إلى المطعم المسموح؛ ليس على اسم عرض قابل للتشابه. تغيير الاسم التجاري لا يعيد توجيه رابط قديم إلى مطعم آخر. سياسة تغيير الـslug وحجز الأسماء القديمة مطلوبة.
- من المنيو يختار العميل الأصناف والإضافات، وتأتي الأسعار من `quote_cart`. لا ينشئ فتح الرابط طلبًا أو سلة دفع أو حجز مخزون. اختيار مطعم آخر يمسح حالة السلة السابقة ولا ينقلها ضمنيًا.
- عند تنفيذ رحلة الشراء لاحقًا، تبقى `prepare_checkout` والهوية وجلسة الموقع والتأكيد الصريح والدفع الخارجي وفق العقد الحالي. لا يضاف شراء تلقائي بسبب رابط أو إعادة فتحه. معاينة المنيو الحالية تظل للاستلام والتسعير فقط؛ هذا القرار لا يعلن اكتمال checkout داخل الواجهة.
- يستطيع المطعم مشاركة رابط ChatGPT نفسه أو رابط نطاقه الخاص أو QR يشير إلى أحدهما. هذه روابط منيو عامة، وليست روابط طاولات ذات صلاحية أو روابط طلبات خاصة. أي دعم لطاولة لاحقًا يحتاج عقده وضوابطه المستقلة.

## 2. عقد الدخول إلى ChatGPT وحدود الإتاحة

توثق [مواصفة OpenAI الرسمية](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#deep-links) الشكل التالي:

```text
https://chatgpt.com/plugins/<plugin-id>/app/<tool-name>?path=<encoded-app-relative-url>
```

نحتاج Global/Sidebar entrypoint يقبل `{}`، ويعرض الدليل عند غياب مسار مطعم. يقرأ التطبيق `hostContext["openai/deepLink"].url` عند التهيئة وعند `ui/notifications/host-context-changed`. يبدأ المسار النسبي بـ`/` ولا يحتوي fragment؛ يرمّز المسار كاملًا، بما فيه query إن وجدت، مرة واحدة كقيمة `path`، وترمّز معرفات الإضافة والأداة وفق المواصفة. مثال تصميمي لمسار عام بلا بيانات شخصية: `/restaurants/demo-a/menu` يصبح `%2Frestaurants%2Fdemo-a%2Fmenu`. معرف الإضافة واسم أداة الدخول النهائيان يثبتان من التسجيل الفعلي، ولا تنشر الأمثلة كرابط عامل.

جدول [دعم المنصات](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#platform-support) يصف دعمًا متوقعًا عند الإطلاق: Desktop وWork web وiOS تدعم deep links، وAndroid غير مدعوم؛ المقصود بالويب Work browser، وليس classic ChatGPT. هذه مواصفة، لا نتيجة قبول لتطبيقنا أو لكل حساب. الإتاحة والتثبيت والتوزيع الخاص وتجربة الجوال تحتاج إثباتًا، ولا تضمن النشر العام. [مرجع Extensions](https://developers.openai.com/plugins/build/extensions) هو نقطة التحقق قبل التنفيذ.

### فجوة التنفيذ المثبتة في المصدر

خط الأساس المفحوص `fdc1d18a87216f7be794604c0155dd7d4ee5a594`:

- يعلن المسار الاصطناعي القديم في [mcp.mjs](../prototype/platform/mcp.mjs) مدخلي Global وThread لأداة الدليل. هذا ليس مدخل المنيو الحقيقي الجديد.
- في مسار `coreAdapter` تفتح `get_restaurant_menu` مورد [core-menu-ui.mjs](../prototype/platform/core-menu-ui.mjs) وتطلب `tenantId`؛ لا تعلن Global entrypoint. لا يوجد استهلاك `openai/deepLink` في واجهة المنيو أو الدليل الحاليين.
- لذلك يلزم مدخل مستقل أو توسيع مدروس للدليل يعرض المنيو الحقيقي ويقبل `{}`، مع توجيه مسارات واختبارات. لا يكفي تركيب URL على أداة المنيو الحالية. تبقى [حدود معاينة المنيو](../prototype/platform/CORE-MENU-UI.md) سارية.

## 3. النطاق الخاص: DNS ثم HTTPS ثم تحويل

المسار المخطط:

```text
https://menu.restaurant.example/
  → نقطة HTTPS تابعة لـOnlinu بشهادة صالحة لهذا الاسم
  → مطابقة hostname موثّق مع مطعم منشور
  → رابط ChatGPT الخاص بمنيو ذلك المطعم
```

سجل DNS التوضيحي، وليس إعدادًا صالحًا للنسخ الآن:

```text
menu.restaurant.example. CNAME <ONLINU_VERIFIED_REDIRECT_HOST>.
```

القيمة بين الأقواس placeholder فقط؛ لا مضيف إنتاج محدد حتى يُختار ويُتحقق منه. يحل CNAME اسم مضيف إلى اسم آخر، ولا يحمل مسار URL ولا يرسل HTTP redirect ولا يصدر شهادة. التحويل عمل خدمة HTTPS بعد التحقق من الاسم والشهادة. لا يوجّه CNAME إلى `chatgpt.com`، ولا يجعل ChatGPT مستضافًا تحت نطاق المطعم. أساس الفصل بين DNS والتحويل: [RFC 1034، الأسماء البديلة](https://www.rfc-editor.org/rfc/rfc1034.html#section-3.6.2) و[RFC 9110، التحويل](https://www.rfc-editor.org/rfc/rfc9110.html#name-redirection-3xx).

نبدأ باسم فرعي مثل `menu` أو `www`. النطاق الجذر `restaurant.example` ليس وعدًا بدعم CNAME قياسي؛ يحتاج حلًا يدعمه مزود DNS مثل ALIAS/ANAME أو flattening، ويختبر منفصلًا دون تغيير MX أو بقية سجلات المطعم. [Cloudflare يوضح flattening عند apex](https://developers.cloudflare.com/dns/cname-flattening/) كمثال تقني، وليس اختيارًا للمزود.

التحويل الأولي `302`، أو `307` إذا اعتمد عقده، مع `Cache-Control: no-store`؛ لا `301/308` دائمة قبل استقرار السياسة تفاديًا لبقاء وجهة قديمة في الكاش. يقبل مسار التحويل GET/HEAD فقط ويرفض POST وبقية الطرق، فلا يمرر جسم طلب إلى ChatGPT. تضبط `Referrer-Policy: no-referrer`. تبقى الوجهة النهائية ظاهرة على ChatGPT؛ لا reverse proxy لصفحاته ولا وعد بإخفاء علامته أو تضمينه في iframe.

## 4. تسجيل النطاق وإثبات ملكيته والشهادة

حالات تشغيل مقترحة، لا مخطط قاعدة منفذ: `pending_verification → pending_tls → active → suspended/removing → released`. تحفظ أدلة الملكية وحالة DNS والشهادة كل على حدة؛ لا تختزل إلى علامة «متصل» واحدة.

1. يضيف مالك المطعم المخوّل اسمًا محددًا. يوحّد الخادم hostname وIDNA وحالة الأحرف، ويمنع IP والمنافذ والمسارات وwildcards والأسماء المحجوزة. سجل فريد ومعاملة/نسخة يمنعان ربط الاسم بمطعمين أو سباق المطالبة.
2. يصدر تحدي TXT عشوائي محدود العمر مربوطًا بالاسم والمطعم ومحاولة التسجيل. يوضع مثلًا تحت `_onlinu-verification.menu.restaurant.example`، منفصلًا عن CNAME. وجود CNAME قديم إلى الخدمة لا يكفي لإثبات حق المستأجر الجديد.
3. يتحقق الخادم من TXT ومن توجيه DNS إلى المضيف المعتمد، مع إعادة فحص الانتشار والفشل والتعارض وCAA عند الحاجة. لا ينفذ جلب HTTP اعتباطيًا إلى مضيف يرسله المستخدم؛ يمنع SSRF إلى العناوين الخاصة والمحلية وخدمات metadata.
4. بعد إثبات الملكية، يهيئ مزود custom hostnames أو ACME شهادة للاسم نفسه وربط SNI الصحيح. إدارة التجديد والتنبيه قبل الانتهاء وفشل التحقق جزء من الخدمة. لا إصدار شهادة تلقائيًا لكل Host وارد ولا إعادة استخدام شهادة نطاق Onlinu للنطاق المخصص.
5. لا يصبح الاسم active قبل نجاح الملكية وDNS والشهادة وربط المطعم ونشره. أي فشل يعرض حالة قابلة للفهم ولا يحوّل إلى مطعم افتراضي. تحديات ACME اللازمة تبقى في مسارها المحلي المقيّد ولا تحوّل إلى ChatGPT.

مرجع التنفيذ عند اختيار المزود: [Cloudflare hostname validation](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/hostname-validation/) يفصل إثبات ملكية الاسم عن قبول الشهادة، ويشترط حالتي active وتوجيه DNS الصحيح. [Let's Encrypt challenges](https://letsencrypt.org/docs/challenge-types/) يشرح تحقق ACME عبر HTTP-01 أو DNS-01. هذه مراجع للمتطلبات؛ لا إنشاء حساب أو طلب شهادة أو إضافة DNS أو إعطاء بيانات اعتماد الآن.

## 5. التوجيه والعزل وإيقاف الخدمة

- جدول موثوق يربط hostname المطابق تمامًا بمطعم واحد ورابط منيو منشور ووجهة ويب معتمدة ووضع تحويل. لا يقبل `tenantId` من query لتجاوز الربط. الـslug ومعرف المطعم تلميح توجيه، لا هوية مستخدم ولا حد تفويض؛ تعيد الأدوات والنواة فحص الصلاحيات الحالية وملكية الطلب.
- على الحافة يطابق الاسم المضيف المصرح به وسياق TLS. لا تثق الخدمة بـ`Host`/`Forwarded`/`X-Forwarded-Host` من الإنترنت وحدها. إن وجدت proxy، تحذف ترويسات العميل وتقبل مصدرًا موثوقًا محددًا فقط، ثم تطابق الاسم مع allowlist؛ يفشل التعارض مغلقًا. لا catch-all يختار أول مطعم.
- تبني الخدمة `Location` بنفسها إلى أصل `https://chatgpt.com` ومعرف الإضافة وأداة الدخول المسجلين فقط. يمنع `next` و`redirect_url` والعناوين المطلقة و`//host` وCRLF وfragment وفك الترميز المزدوج أو path traversal. أسماء المطاعم لا تدخل HTML دون escaping.
- روابط المنيو عامة ولا تحتوي اسم عميل أو هاتفًا أو عنوانًا أو رمز OAuth أو جلسة أو مفتاحًا أو سر طلب/دفع. لا تنقل cookies أو Authorization إلى الوجهة. تسجل الأحداث التشغيلية بقدر محدود ومنقح، دون query خام أو بيانات عملاء.
- تعليق المطعم/النطاق أو إلغاء نشره يوقف فتح المنيو الجديد والتحويل فورًا ضمن سياسة الكاش المختبرة. يمسح كاش الربط، ولا يقطع مسار تسوية طلبات قائمة أو استرداداتها. تغيير المطعم المستهدف يستلزم مسارًا إداريًا صريحًا وتدقيقًا؛ لا تبديل ضمني.
- عند الإزالة يُعطل التحويل والربط أولًا، ثم يُطلب حذف CNAME، وتزال تهيئة custom hostname ومادة الشهادة وتوقف تجديداتها؛ تنفذ سياسة إبطال الشهادة المعتمدة لدى CA عند الحاجة. يحتفظ النظام بحجز/tombstone يمنع الاستيلاء عبر DNS متروك. لا إعادة مطالبة حتى دليل ملكية جديد وفحص DNS وتحرير مأذون؛ لا تكفي معرفة hostname أو انتهاء اشتراك سابق.
- تختبر إعادة التفعيل ونقل الملكية وانتهاء الشهادة وفقد السيطرة على DNS وإبطالها. لا يعاد تشغيل اسم معلّق أو منتهي تلقائيًا لمجرد عودة إجابة DNS.

## 6. البديل الواضح واختبارات الأجهزة

يدعم التصميم وضعين يختارهما مالك المطعم عند التفعيل لاحقًا: تحويل مباشر إلى ChatGPT، أو صفحة وصول تحمل زرّي «افتح في ChatGPT» و«تصفح منيو الموقع». لكل وضع وجهة ويب معتمدة للمطعم نفسه ومسار وصول واضح لها؛ صفحة الاختيار هي الخيار الأول للتجربة العامة إلى أن يثبت التوافق. لا يختار هذا المستند وضعًا نيابة عن مطعم فعلي.

لا يدعي User-Agent معرفة تثبيت الإضافة أو تسجيل الدخول أو نجاح فتح التطبيق. بعد الانتقال إلى ChatGPT قد لا تستطيع خدمتنا كشف الفشل أو إعادة المستخدم؛ لا وعد بـfallback تلقائي. يختبر المسار البديل الظاهر قبل الانتقال، وإلغاء تسجيل الدخول/التثبيت والعودة إلى صفحة الوصول دون حلقة. موقع المطعم يبقى مستقلًا عن ChatGPT، ولا تُطلب صلاحيات إضافية لتصفح رابط عام.

التوزيع الخاص الحالي ليس دليلًا على إتاحة رابط لجمهور المطعم أو على فتحه في كل تطبيق جوال. يسجل القبول لكل حساب/خطة وإصدار وOS وسطح: Desktop، Work web، iOS، وAndroid/classic web كحالات عدم دعم أو توافق يحتاج إثباتًا جديدًا. تشمل المصفوفة مستخدمًا غير مسجل، إضافة غير مثبّتة، حسابًا خارج نطاق التوزيع، وإلغاء OAuth واستئنافه. لا نعد بتجاوز شروط OpenAI أو قبول النشر العام.

## 7. ترتيب التنفيذ وبوابات القبول

بعد أعمال الأمن والمفاتيح وقبول الدفع الحالية: (1) مدخل الدليل والمنيو والتوجيه الداخلي ببيانات اصطناعية، (2) قبول الرابط في حسابات وأجهزة وتوزيع محدد، (3) اختيار مزود النطاقات والتكلفة والتشغيل، (4) خدمة التحويل وإثبات الملكية والشهادات، (5) تجربة نطاق واحد مأذون ثم تدرج. نجاح خطوة لا يغلق التالية؛ يبقى [سجل الإطلاق](SAAS-LAUNCH-GATES.ar.md) حاكمًا للإنتاج.

| البوابة | الدليل المطلوب قبل التفعيل |
| --- | --- |
| DL01: المدخل والمسار | `{}` يفتح الدليل؛ رابطان لمطعمين يفتحان الصحيح؛ رفض المسار غير المعروف والترميز الفاسد/المكرر والـfragment؛ تحقق التهيئة وتغير host context |
| DL02: العزل والحالة | تبديل المطعم وBack/Forward وإعادة الفتح والردود المتأخرة لا يعرض سلة/سعر مطعم آخر؛ مطعم غير منشور/معلّق يفشل مغلقًا؛ الرابط لا يمنح قراءة طلب ولا ينفذ كتابة |
| DL03: الإتاحة | فتح حقيقي لكل سطح وحساب مستهدف، مع عدم التثبيت والدخول والإلغاء والتوزيع الخاص؛ نتيجة Android وclassic web لا تُفترض؛ البديل ظاهر ويصل إلى المطعم نفسه |
| CD01: الملكية | TXT خاطئ/منتهي/معاد استخدامه يفشل؛ duplicate/concurrent claim مرفوض؛ CNAME وحده لا يسمح بإعادة استيلاء؛ نطاق غير موثق لا يحوّل |
| CD02: HTTPS وDNS | اسم وشهادة متطابقان، انتشار/انقطاع DNS وCAA وفشل الإصدار/التجديد/الانتهاء؛ ACME يعمل دون تحويل تحديه؛ لا تحويل قبل اكتمال الحالات |
| CD03: التوجيه الآمن | تزوير Host/forwarded headers واسم مجهول وCRLF وopen redirect وSSRF وPOST تفشل؛ الرابط النهائي allowlisted؛ لا أسرار أو PII في URL أو logs |
| CD04: دورة الحياة | تعليق وإزالة ومحو كاش وربط وشهادة وتجديد، DNS متروك، نقل ملكية وإعادة مطالبة موثقة، دون تحويل إلى مطعم آخر أو تعطيل تسوية طلب قائم |
| CD05: التشغيل | مزود ومضيف فعليان موثقان، تكلفة وحدود وتجديد ومراقبة ومسؤول تشغيل وسياسة إزالة/رجوع؛ لا رسوم أو إعدادات حية قبل الموافقة المناسبة |

كل البوابات أعلاه **مفتوحة وغير مختبرة لهذا التصميم**. التحقق في هذا التحديث يقتصر على قراءة المصدر والمراجع وفحص اتساق الوثائق والروابط؛ لا اجتياز CI أو قبول DNS/TLS/ChatGPT بسبب تعديل خطة.
