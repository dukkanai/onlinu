# تجربة منصة المطاعم المحمية على النطاق

هذه ملفات نشر تجريبي مستقل على `https://almujeeb.info` ببيانات مطعمين وعملاء اصطناعيين فقط. ليست إطلاقًا تجاريًا، ولا اعتمادًا لمكان الخادم الحالي لإقامة بيانات العملاء داخل السعودية. الدفع محاكاة محلية فقط، ولا توجد بيانات دفع أو طلبات حقيقية.

يستخدم المشروع اسم Compose مستقلًا `restaurant-saas-staging` وصورًا وvolumes وشبكات منفصلة. تبقى تجربة loopback السابقة على `18787` وخدمة AstraCalls القديمة على `8080` كما هما. منصة التجربة الجديدة على `127.0.0.1:18788` وDex على `127.0.0.1:15556`؛ لا تُنشر قواعد البيانات على المضيف.

ينضم Dex وحده إلى bridge عادية باسم `identity-ingress` لتمكين نشر منفذه على loopback؛ Docker لا ينشر المنفذ عندما تكون جميع شبكات الحاوية داخلية. تظل قاعدة الهوية على شبكة `identity-data` الداخلية، ولا تشارك المنصة شبكة Dex.

## المصادقة وحدود التجربة

الدخول بحسابات اختبار محددة مسبقًا عبر Dex/OIDC، وليس اختيار هوية من واجهة التطوير. يتمثل كل مختبِر في حساب اصطناعي، ولا يُفتح تسجيل عام أو ربط حسابات ذاتي. جهة الإصدار `https://almujeeb.info/identity` والعميل `restaurant-staging-web`، وعودة OIDC إلى `/auth/callback`. يجب مطابقة مسارات التطبيق قبل التشغيل.

Dex الرسمي مثبت على الإصدار `v2.45.1` والبصمة `sha256:8499afd690c437f52301efd2b05b2455da5bd2dfc20332cd697dc9937f808462` ويعمل بمستخدم `dex:dex`. يسمح بتدفق authorization code فقط؛ لا password grant أو implicit flow. كلمات مرور المختبرين عشوائية، ولا يحتوي إعداد Dex إلا تجزئات bcrypt لها. هوية الإدارة محفوظة في قاعدة PostgreSQL مستقلة بدور غير superuser.

يُحظر `/dev` و`/dev/*` على Caddy وكذلك داخل التطبيق في وضع OIDC. مهام MCP المقيدة تحتاج رمز OAuth صحيحًا وصلاحياته؛ بوابة الويب ليست بديلًا عن فحص ملكية الطلب أو عضوية موظف المطعم. وجهة OAuth الخاصة بربط ChatGPT محددة حرفيًا دون wildcard.

تحديد المعدل الحالي في المنصة يعتمد عنوان اتصال الوكيل، ولذلك يشترك مستخدمو staging خلف Caddy في الحد نفسه؛ ليس حدًا مستقلًا لكل عميل. ولا تمر صفحات دخول Dex عبر محدد معدل التطبيق. هذا حد معلوم لتجربة قليلة المختبرين، وليس تصميم حماية التوافر للإنتاج؛ يتطلب الإطلاق التجاري تحديد معدل عند المدخل لكل عميل وحماية من الإغراق، مع سياسة ثقة صريحة للوكيل قبل اعتماد أي عنوان مُمرّر. لم تُضف ثقة عامة بترويسات `X-Forwarded-For`.

## تحضير الأسرار

شغّل مولد الأسرار محليًا بعد اكتمال مراجعة المصادقة:

```bash
node prototype/staging/generate-secrets.mjs
```

يعتمد المولد على `bcryptjs@3.0.3` الموجود في dependencies التطوير الخاصة بالمنصة. ينشئ `/home/chatbot/.local/share/almujeeb-staging` بصلاحية `0700` ويطبع مساره فقط. يرفض إعادة الاستخدام أو استبدال مجلد قائم، حتى إن كان فارغًا. لا تعِد توليد الأسرار لvolumes موجودة؛ تغيير كلمة مرور ملف لا يغير كلمة مرور دور PostgreSQL تلقائيًا.

ملف `testers.json` بصلاحية `0600` مخصص للتسليم الخاص للمختبرين؛ لا يُرفع للمستودع أو الموقع ولا يُطبع في السجلات. ملفات الخدمات `0444` تحت المجلد الخاص وتُركّب للقراءة فقط داخل الحاوية التي تحتاجها. لكل قاعدة كلمة مرور bootstrap وكلمة مرور تطبيق مختلفتان عشوائيتان. لا تستخدم الخدمات دور bootstrap.

## فحوص قبل أي تشغيل خارجي

```bash
node --check prototype/staging/generate-secrets.mjs
bash -n prototype/staging/init-app-db.sh
docker compose -f prototype/staging/compose.yml config --quiet
caddy adapt --config prototype/staging/Caddyfile --adapter caddyfile --validate >/dev/null
```

يجب أن تنجح فحوص OIDC والجلسات وحماية CSRF والعزل أولًا، وأن تدعم المنصة والخدمتان ملفات الأسرار `*_FILE`. جهّز صور staging دون إعادة وسم صور prototype أو الإنتاج:

```bash
docker compose -f prototype/staging/compose.yml build platform tenant-a tenant-b
```

هذه الأوامر لا تبدأ الخدمات. لا تستخدم ملف Compose القديم لتشغيل هذه التجربة. حدود الذاكرة المعلنة لجميع الخدمات الجديدة تقارب 1.5GiB؛ راقب الاستهلاك الفعلي أثناء التشغيل ولا تبنِ الصور الثقيلة بالتزامن مع نقص الذاكرة.

## التوجيه والتشغيل بعد قبول الفحوص

طُبق ملف `Caddyfile` هنا على `/etc/caddy/Caddyfile` بعد قبول فحوص المصادقة بتاريخ 30 سبتمبر 2026، وفُعّلت خدمة Caddy. كان الإعداد السابق غير المشغّل يوجّه النطاق إلى التطبيق القديم؛ لا تستعد ذلك التوجيه عند تحديث بيئة الاختبار. التوجيه الحالي هو:

- `/identity` و`/identity/*` إلى Dex على `15556` مع الإبقاء على البادئة، دون `handle_path`.
- بقية المسارات إلى منصة staging على `18788`، بلا رجوع إلى الخدمة القديمة.
- HTTP يتحول إلى HTTPS تلقائيًا بواسطة Caddy. لا يلزم تغيير DNS أو إضافة `www` لهذه المرحلة.

حد الطلب 64KiB، والسياسة الافتراضية `Referrer-Policy: no-referrer`. صفحة موافقة OAuth وحدها تضبط `same-origin` في الاستجابة ووسم meta؛ تبقى الإحالات الخارجية بلا Referer، بينما يُرسل نموذج الموافقة أصله الصحيح للخادم. هذا يعالج إرسال المتصفح `Origin:null` للنموذج تحت `no-referrer` بحسب [معيار Fetch لإضافة Origin](https://fetch.spec.whatwg.org/#append-a-request-origin-header)، دون قبول `Origin:null` أو تعطيل CSRF. كذلك يقتصر `form-action` في صفحة الموافقة وردها على الموقع وعنوان العودة المعتمد حرفيًا.

لا تُفعّل access logs التي تسجل رموز OAuth أو بيانات نموذج الدخول، ولا تطبع مخرجات `docker inspect` الكاملة أو ملفات الأسرار عند التشخيص. لا يحتاج فحص المنافذ أو DNS أو صحة الخدمات إلى كشفها.

اكتشاف OIDC في التطبيق مؤجل إلى بدء تسجيل الدخول، فلا يتطلب تشغيل المنصة أن يكون الوكيل متاحًا مسبقًا. يبدأ المشغل الخدمات المستقلة بعد قبول فحوصها، ثم يطبق إعداد Caddy المقبول ويختبر discovery على HTTPS، ثم تسجيل الدخول. لا يُعتبر ظهور صفحة تسجيل الدخول إثباتًا لاكتمال المصادقة؛ اختبر الدخول والخروج ومنع جلسة من الوصول لطلبات أو إدارة مطعم آخر.

بعد التشغيل افحص بقاء `18787` و`8080` والحاويات القديمة كما هي، ونجاح HTTPS، وتعذر الوصول المباشر لقواعد البيانات، ورفض `/dev/*`، ومنع المستخدم غير المصرح له من طلبات العميل وإدارة المطعم. لا تُعد هذه الملفات إثباتًا لاختبار ChatGPT فعليًا أو استقبال MCP Events من حساب حقيقي؛ ذلك يحتاج اختبار التكامل المعني.

المستخدم رفض snapshot/backup في هذه المرحلة؛ لم تُنشأ نسخة ولا لقطة، ولا تتضمن هذه الخطوات إجراءً ينشئهما. لا تستخدم `docker compose down -v` أو حذف volumes لأي من المشاريع. عند إيقاف التجربة استخدم اسم مشروع staging وحده، وأبقِ بيانات وعمليات المشروعين السابقين دون مساس.

## دليل القبول المسجل في 30 سبتمبر 2026

- تشغيل مشروع `restaurant-saas-staging` مستقل على المضيف الحالي، بصحة المنصة وقواعده الأربع. منافذ المنصة والهوية على loopback فقط، ولا قواعد بيانات منشورة. أثبت اختبار Dex العملي ضرورة شبكة `identity-ingress` العادية لنشر منفذه؛ قاعدة الهوية لا تزال على الشبكة الداخلية وحدها.
- استجابة HTTPS الصحيحة لـ`GET /health` واكتشاف OIDC، وتحويل HTTP إلى HTTPS. يرد `/dev/session` بحالة404، وترد واجهة البيانات على غير المسجل بحالة401. اختبار المتصفح اتصل بعنوان النطاق HTTPS من هذا المضيف؛ ليس قياس توافر عالميًا أو اختبار تحميل.
- مجموعة المنصة: **87/87** بلا تخطٍّ، مع PostgreSQL16 حقيقي معزول لتكامل الهوية والقنوات والأحداث وحماية HTTP. ثم **3/3** فحوص إضافية لضبط الإتاحة الخارجية ورفض الأسرار التجريبية وإعداد الهوية غير الآمن. اختبار ملفات أسرار خدمة Go: **1/1**. `npm audit --omit=dev --audit-level=moderate` بلا ثغرات معروفة وقت الفحص؛ لا يشمل ذلك جميع صور نظام التشغيل.
- واجهة المتصفح باستجابات محاكية: **29 تحققًا**. الاختبار الفعلي عبر HTTPS وDex: **148 تحققًا**، أربعة حسابات موثقة، وطلبان وهميان أُنشئا واكتمل مسارهما بمحاكاة الدفع. شمل عزل العملاء والمطاعم وCSRF وصفات ملفات الارتباط، وتعارض نسخ إعداد القناة ثم إعادة قيمه، والخروج ورفض إعادة استخدام الجلسات الملغاة.
- OAuth وMCP على النطاق: **106 تحققات ناجحة** في التشغيل النهائي، تشمل تفويضين فعليين من المتصفح بصلاحيات كاملة ثم محدودة، PKCE ومنع إعادة استخدام الكود، اكتشاف أدوات MCP وصلاحياتها، المنيو والتسعير وتجهيز رابط تأكيد دون إنشاء طلب، ومنع تجاوز الصلاحيات وإبطال الرموز. بعد إصلاح سياسة الموافقة أُعيدت الاختبارات الأمنية المتأثرة: **13/13** بلا تخطٍّ، مع استمرار رفض `Origin:null` حتى مع CSRF صحيح.
- التقط اختبار OAuth النهائي وجهتَي العودة إلى ChatGPT بواسطة CDP قبل الشبكة، مع حظر DNS لكل مضيف غير نطاق التجربة. أثبت أنهما GET بلا Referer أو Authorization أو body؛ هذا إثبات للتشغيل النهائي المعزول، لا لقبول حساب ChatGPT. محاولة تشخيصية أسبق وصلت302 ولم تلتقطها آلية الاختبار القديمة، لذلك لا ندعي إثبات عدم اتصالها بالوجهة؛ لم يصدر فيها access token أو يُنشأ طلب، وكان الكود قصير العمر ومقيدًا بـPKCE.
- حاويتا النظام الأصلي بقيتا صحيتين وبوقت بدء التشغيل السابق، والنموذج المحلي `18787` لم يُعَد تشغيله. لم يغيَّر ترخيص أو اتصال واتساب الأصلي أو بياناته. أُزيلت فقط بيانات قواعد الاختبارات المؤقتة المعزولة؛ يبقى الطلبان الوهميان داخل قواعد staging كأثر للاختبار.
