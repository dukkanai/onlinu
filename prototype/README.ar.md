# النموذج المعزول لتحويل المطاعم إلى SaaS وChatGPT

تاريخ النتيجة: 30 سبتمبر 2026. هذه حزمة تنفيذ واختبار اصطناعية مستقلة، وليست نسخة إنتاج أو نقلًا مكتملًا لخصائص المشروع الأصلي. لا تستخدم قاعدة المطعم الحالية أو واتساب أو أموالًا وبيانات شخصية حقيقية. القرار الحالي **إضافة ChatGPT وFlutter مع إبقاء واتساب QR وCloud API وتراخيصه وجميع قوالب الويب وإدارة الويب**؛ لا حذف ولا استبدال للنظام الأصلي.

## ما أُنجز

- منصة مركزية تعرض مطعمين تجريبيين وتوجّه العمليات إلى خدمة Go وقاعدة PostgreSQL مستقلتين لكل مطعم. صور التشغيل موحدة؛ إعدادات المطعم وصلاحياته وحجمه التخزيني وشبكته منفصلة. لا يوجد Docker socket داخل التطبيقات.
- مسار بحث ومنيو وتسعير من الخادم ثم رابط صفحة ويب للمراجعة والتأكيد. تجهيز الرابط لا ينشئ الطلب ولا يحجز مخزونًا. التأكيد الصريح ينشئ طلبًا واحدًا مع حجز معاملاتي للمخزون، ويحافظ على النتيجة عند إعادة المحاولة وانقطاع الرد وانتهاء صلاحية السلة بعد إنشاء الطلب.
- نقطة `/mcp` باستخدام حزمة MCP الرسمية الجديدة، بروتوكول `2026-07-28`، وخمس أدوات: البحث، والمنيو، والتسعير، وتجهيز رابط التأكيد، وحالة الطلب. مورد واجهة Extensions بموضعي `global` و`thread`. لا تُعرض أدوات إدارة المطعم أو محاكاة الدفع للنموذج.
- اشتراكات MCP Events محفوظة في PostgreSQL، وOutbox معاملاتي داخل المطعم، وتوقيع Webhook وتحقق تحدٍّ، وتشفير مفاتيح التوقيع، ومنع العناوين الداخلية وDNS rebinding والتحويلات، وإعادة محاولة محدودة مع إزالة الازدواج. يراجع النظام ملكية الطلب عند الاشتراك والإرسال؛ إبطال الرمز يلغي اشتراكات صاحبه الحالية ومحاولاتها المعلقة.
- OAuth تجريبي بــPKCE S256، وتقييد دقيق لـredirect/resource، ورموز قصيرة العمر محفوظة كبصمات، واستهلاك الكود مرة واحدة. الصلاحيات الضيقة مطبقة على MCP وREST معًا. **اختيار الهوية الوهمية ليس تسجيل دخول إنتاجيًا.**
- محول ميسر **للاختبار فقط**، يراجع الفاتورة لدى ميسر قبل قبول السداد ولا يثق بعودة المتصفح أو محتوى webhook. إذا كانت نتيجة إنشاء الفاتورة مبهمة يسجل «تحتاج مراجعة» ولا يكرر إنشاء عملية مالية تلقائيًا. لم يتصل هذا النموذج بحساب ميسر حقيقي حتى الآن. الإعداد التجريبي يقبل مفتاح اختبار واحدًا؛ إدارة مفاتيح وحسابات منفصلة لكل مطعم والتسوية المباشرة له لم تُنفّذ بعد، وهي شرط قبل قبول مسار المال متعدد المطاعم.
- تطبيق إدارة Flutter عربي RTL يبدأ بويندوز: عضوية المطعم، قائمة الطلبات، انتقالات الحالة مع رقم النسخة، وحجب الكتابة بعد فشل الاتصال إلى أن ينجح تحديث. الرموز في الذاكرة فقط. تفاصيله في [دليل Flutter](admin_flutter/README.md).
- مسار staging منفصل على النطاق الرئيسي `almujeeb.info`، بدخول OIDC عبر Dex وحسابات اختبار محددة، ومنع اختيار هوية التطوير. أسراره مستقلة خارج المستودع، وأربع قواعد منفصلة للمنصة والمطعمين والهوية. تعليمات التشغيل والحدود في [دليل staging](staging/README.ar.md). موافقة نشر بيئة الاختبار لا تعني قبول الإنتاج أو تجربة حساب ChatGPT نفسه.
- إعداد واتساب لكل مطعم، مع اختيار QR أو Cloud API ورقم نسخة وسجل تدقيق. هذه **إعدادات اصطناعية محفوظة فقط**؛ `configured:false` و`operational:false` حتى يُربط محول القناة بخدمة واتساب الأصلية. لا يفصل هذا الإعداد خدمة واتساب الحالية أو يعطلها.

التصميم والمواصفات الدقيقة في [عقد النموذج](CONTRACT.md)، و[خطة التحول](../plans/SAAS-TRANSFORMATION-PLAN.ar.md)، و[بوابات قبول الإطلاق](../plans/SAAS-LAUNCH-GATES.ar.md)، و[خريطة إعادة استخدام المشروع الأصلي](../plans/SAAS-REUSE-MAP.ar.md).

## تشغيل العرض المحلي

من هذا المجلد:

```bash
docker compose -f compose.yml up -d --build --wait
docker compose -f compose.yml ps
```

افتح `http://127.0.0.1:18787` على الجهاز الذي يشغّل Docker. المنفذ منشور على loopback فقط؛ لا تفتحه للعامة ولا تنقل هذه الإعدادات إلى الإنتاج. إن كان المضيف بعيدًا يمكن الوصول إليه عبر تحويل منفذ SSH مصادق عليه إلى عنوان loopback نفسه، مع عدم إتاحة النفق للآخرين.

1. اختر `customer-alice` ثم «دخول تجريبي»، واختر المطعم والكمية واحسب السلة.
2. انتقل إلى صفحة التأكيد، واختر العميل الوهمي نفسه عند طلب ذلك. رابط الصفحة وحده لا يتيح بيانات السلة.
3. أكّد الطلب ثم اضغط «محاكاة نجاح الدفع محليًا». هذه ليست عملية ميسر ولا تُسحب أموال.
4. افتح الصفحة الرئيسية بهوية `merchant-a` أو `merchant-b`، أو شغّل Flutter على Windows، لمشاهدة طلبات المطعم الصحيح وتحديثها. شاشة إدارة الويب هنا وسيلة فحص مساعدة، لا بديل قرار Flutter.

`demo-a`: الوجبة 30 ريالًا والمشروب 5 ريالات. `demo-b`: الوجبة 45 ريالًا والمشروب 7 ريالات. المخزون الابتدائي 30 لكل صنف؛ الاختبارات والطلبات الوهمية تستهلكه فعلًا وتبقى في أحجام البيانات. لا يجمع هذا النموذج الاسم أو الهاتف أو عنوان التوصيل.

لإيقاف هذه الحزمة فقط مع إبقاء بياناتها التجريبية:

```bash
docker compose -f compose.yml stop
```

لا تستخدم حذف الأحجام لإصلاح مشكلة أو أثناء الترحيل؛ لا يحتاج التشغيل المعتاد ذلك. لم تُعدّل حاويات المشروع الأصلي أو أحجامها أو منافذها.

## حدود الأمان والاستضافة

قيم كلمات المرور ومفاتيح الخدمة والتشفير في `compose.yml` المحلي **قيم تجريبية مكشوفة عن قصد**، ولا تصلح لأي بيانات حقيقية. جميع الشاشات والهويات اصطناعية. يمنع الكود تعريض وضع اختيار الهوية للخارج ولو ضُبط `PROTOTYPE_ALLOW_REMOTE`؛ الإتاحة الخارجية تتطلب وضع OIDC المحمي وإعداد `staging/compose.yml` بأسرار مستقلة. لا يُنشأ snapshot أو backup في هذه المرحلة بناءً على قرار المالك؛ هذا لا يلغي شرط النسخ والاستعادة قبل الإنتاج.

الخدمات تعمل دون root، وبنظام ملفات للقراءة فقط، وإسقاط الامتيازات وحدود موارد. قواعد البيانات لا تنشر منافذ للمضيف؛ لكل منها مستخدم تطبيق غير superuser، ولا تصل المنصة إلى شبكة قاعدة المطعم مباشرة. تبقى الحاويات مشتركة في نواة المضيف؛ ليست عزلًا ماديًا، ولا حماية من اختراق المضيف، ولا توافرًا عاليًا.

اختيار الإنتاج المعتمد: VPS داخل السعودية يديره المالك، مع بقاء **قواعدنا وصورنا وملفاتنا وسجلاتنا ونسخنا الاحتياطية المخزنة** داخل السعودية. النموذج الحالي لا يثبت موقع مضيفه ولا يعد شهادة إقامة بيانات؛ لذلك لا يحتوي بيانات حقيقية. معالجة ChatGPT ونسخه لدى مزوده خارج ضمان استضافتنا، مع تقليل البيانات المرسلة والإفصاح للمستخدم.

يحتاج الإنتاج أيضًا أسرارًا مستقلة آمنة وتدويرها، وتسجيل دخول فعليًا، وفصل صلاحيات الترحيل عن التشغيل، وحماية معدل الطلبات على الحافة، وصيانة وثغرات وصور مثبتة ومدققة، ونسخًا سعودية مشفرة خارج المضيف واختبار استعادة، ومراقبة وتنبيهات. إعادة تشغيل الحاويات بنجاح ليست اختبار استعادة نسخة احتياطية أو إثبات تحمل 1000 مطعم.

## نتيجة مرحلة النطاق المحمي

نُشرت بيئة الاختبار على [almujeeb.info](https://almujeeb.info) بعد تعطيل مسارات اختيار الهوية فيها، دون تعريض الخدمة الأصلية أو تغييرها. نجحت **87/87** من اختبارات المنصة باستخدام PostgreSQL حقيقي للاختبارات التي تحتاجه، و**3/3** اختبارات إضافية لإعداد الإتاحة الآمن. ونجح **29 تحققًا** لواجهة staging المحاكية، ثم **148 تحققًا عبر HTTPS وDex فعليين**: أربعة حسابات اختبار، وطلبان وهميان مكتملان، وعزل العملاء والمطاعم وحماية CSRF والخروج وإعداد القناة مع إعادة قيمه.

نجح أيضًا اختبار OAuth وMCP على النطاق في **106 تحققات**: موافقة فعلية من المتصفح، PKCE وصلاحيات محدودة وإبطال الرموز، وأدوات المطعم وتجهيز رابط التأكيد دون شراء. اعترض الاختبار النهائي عودة ChatGPT محليًا قبل الشبكة مع حظر DNS للوجهات الأخرى؛ لم يختبر حساب ChatGPT نفسه. أُعيدت **13/13** من اختبارات المصادقة المتأثرة بعد إصلاح سياسة صفحة الموافقة، دون تخفيف فحص Origin أو CSRF.

سجل النشر وحدود الإثبات وأوامر إعادة الاختبار في [دليل بيئة النطاق](staging/README.ar.md). بيانات حسابات الاختبار محفوظة في ملف خاص خارج المستودع، ولا تظهر في هذا الدليل. لم ينفذ backup أو snapshot بطلب المالك. نقطة التكامل المعتمدة هي `https://almujeeb.info/mcp`؛ نجاح الاختبارات لا يعني أن حساب ChatGPT الخاص بالمالك رُبط فعليًا أو أن نشر الإضافة اعتُمد.

## التحقق المسجّل للمرحلة المحلية الأولى

الاختبارات موجهة إلى مخاطر المال والعزل والهوية والتزامن والأحداث؛ لا تستدعي نموذج OpenAI ولا تنفق توكنز API. لا حاجة لإعادتها كلها عند تعديل نص أو لون؛ أعد المجموعة المتأثرة وحدود تكاملها.

| الطبقة | الدليل وحدوده |
|---|---|
| خدمة المطعم Go | PostgreSQL فعلي و`-race`: التزامن، نفاد المخزون، عزل المالك والمطعم، لقطة السعر، الحالات، rollback للأحداث، مرجع الدفع، ثم اختبار استعادة الطلب بمفتاحه. |
| المنصة | نجحت **53/53**، بلا تخطٍ: OAuth/المتجر/MCP/Events/ميسر. اختبارات Events تستخدم PostgreSQL فعليًا في schema منفصل. ميسر يستخدم استجابات اختبار محقونة، لا حساب تاجر. |
| رحلة HTTP بين الحاويات | نجحت رحلة طلب فعلية عبر المنصة وخدمة المطعم وقاعدتيهما؛ تكرار التأكيد لا ينشئ طلبين، ومنع الوصول العابر للمطاعم والعملاء، وعدم قبول تجهيز طلب غير مدفوع. |
| OAuth وMCP عبر Docker | نجحت 8 حالات، يحسبها Node 9 مع الاختبار الحاوي: بروتوكول وأداة وواجهة، S256 وكود مرة واحدة، صلاحيات ضيقة على REST، ورفض webhook داخلي وإبطال الرمز. |
| سلسلة الأحداث | نجح Outbox الحقيقي إلى المؤشر الدائم فالحمولة الموقعة، ثم منع التكرار وتوقف التسليم بعد الفصل. المستقبل محقون للاختبار؛ ليس ChatGPT فعليًا. |
| الثبات | نجحت إعادة تشغيل تطبيق المنصة وخدمتي المطعم مع بقاء الجلسة والسلة والطلب المدفوع ومفاتيح عدم الازدواج. قواعد البيانات وأحجامها لم تُحذف. |
| شبكة قواعد البيانات | رُفض اتصال TCP مباشر من حاوية المنصة بقاعدتي المطعمين عبر عنوانيهما الداخليين؛ مستخدم قاعدة المنصة ليس superuser ولا يملك إنشاء قواعد أو أدوار. هذا فحص محدود، لا اختبار اختراق شامل. |
| Flutter | `flutter analyze --no-pub` بلا ملاحظات و12 اختبارًا ناجحًا؛ لم يُبنَ EXE أو يُختبر Windows فعليًا في مضيف Linux. |
| متصفح Chrome | نجح **25 تحققًا** لردود الهوية والمنيو والسلة المتأخرة ومنع استخدام زر قديم وتكرار الدفع؛ الدليل وصحة الخدمة حقيقيان، وسيناريوهات السباق تستخدم REST وجسر ChatGPT محاكيين. راجعت لقطات RTL؛ ليس اختبارًا داخل ChatGPT. |
| التبعيات | `npm audit --omit=dev --audit-level=moderate`: صفر ثغرات معروفة وقت الفحص. ليس شهادة خلو مطلقة أو فحصًا لصورة نظام التشغيل. |

أوامر التحقق من مجلد `platform/` بعد تشغيل Compose:

```bash
npm ci --ignore-scripts --no-audit --no-fund
npm test
npm run test:integration
node integration/browser-check.mjs
node integration/durability-check.mjs
```

`npm test` يتخطى اختبار PostgreSQL للأحداث إن لم يُضبط `TEST_DATABASE_URL` لقاعدة **تجريبية فقط**؛ لا تعتبر التخطي قبولًا. اختبار الثبات يعيد تشغيل حاويات النموذج؛ شغّله منفردًا بعد انتهاء بقية الاختبارات. فحص المتصفح يحتاج Chrome/Chromium محليًا ولا ينزل متصفحًا تلقائيًا.

من مجلد النموذج، لاختبار توصيل الأحداث الفعلي بمستقبل محقون:

```bash
docker compose -f compose.yml exec -T platform node integration/pipeline-check.mjs
```

ينشئ هذا الفحص schema اختبارية مؤقتة ويحذفها بعده، ويترك طلب مشروب وهميًا داخل المطعم B. لا يتصل بعنوان callback خارجي أو OpenAI. اختبارات المتجر تشمل حقن فقد الرد وفشل حفظ رابط الطلب واستعادته بعد انقضاء صلاحية السلة؛ هذه ليست أعطالًا مالية حقيقية.

## ما لم يُنفّذ بعد، وترتيب العمل التالي

1. **قبول خارجي مضبوط:** تجربة الإضافة وExtensions وEvents على حساب ChatGPT مؤهل عبر HTTPS، وتجربة ميسر بحساب الاختبار ومفاتيح تُدخل عبر قناة أسرار، وتشغيل تطبيق Flutter على Windows فعلي. النجاح البروتوكولي المحلي لا يضمن قبول حساب أو نشر إضافة.
2. **فصل المجال الأصلي:** نقل وظائف المطعم الحالية تدريجيًا إلى خدمة مستقلة مع حفظ سلوك البوابات والمناديب ومناطق التوصيل والطلبات والاستردادات. النموذج المصغر لا ينقلها تلقائيًا ولا يُعد بديلًا مكتملًا لها. رمزا `classic` و`bistro` يثبتان فصل إعداد القالب فقط؛ لا يثبتان تكافؤ قوالب الويب الأصلية.
3. **جاهزية SaaS والإدارة:** إنشاء/تعليق مطعم وعزل حياته ونسخه وترقياته، واشتراكات المنصة منفصلة عن مال المطعم، وهوية وأدوار إنتاجية، وتكافؤ إدارة Flutter والطباعة والتنبيهات وتوقيع وتحديث Windows. Android وiOS لاحقًا. السعر المعتمد في الخطة لا يعني أن فوترة الاشتراك نُفّذت.
4. **تشغيل سعودي وقبول تعافٍ وحمل:** مواصفات VPS ووجهة نسخ مستقلة، وتحقق جغرافي للتخزين، واختبار استعادة وأمن وسعة مناسب لـ30 مطعمًا ثم التوسع المقاس إلى1000؛ لا نفترض أن مضيفًا واحدًا يكفي الجميع.
5. **ربط القنوات مع الحفاظ على المشروع:** إبقاء واتساب QR وCloud API وتراخيصهما وإضافة تفعيل وتعطيل حقيقيين لكل مطعم في مسار إنشاء الطلب، دون تغيير سلوك الويب أو القوالب. المصدر الحالي يحول طلب QR إلى نص webhook/Chatwoot، وMeta webhook يختار أحداث المكالمات؛ دخول هذه الرسائل تلقائيًا إلى سجل طلبات المطعم لم يثبت من المصدر وحده. يجب فحص أي أتمتة خارجية وبناء المحول الناقص قبل ادعاء اكتمال طلب واتساب. حقوق المكتبات وبيانات الجغرافيا تبقى محفوظة.

النطاق الرئيسي معتمد وحساب المالك ChatGPT Pro. تبقى تجربة الربط الفعلية من حسابه، ومضيف السعودية ووجهة النسخ عند النقل، وحساب اختبار ميسر وWindows عند قبولهما. لا ترسل المفاتيح أو كلمات المرور في المحادثة. لا يلزم عقد خاص يضمن إقامة ChatGPT في السعودية وفق النطاق الذي اعتمدته.
