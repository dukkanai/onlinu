# Synthetic MCP Events implementation

Reference: [OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events), fetched 2026-09-30. Implementing the server side does not establish access to ChatGPT Events or prove a live subscription in a particular account.

- `order.status_changed` is customer-only and requires an owned `tenantId` / `orderId`. The payload includes status, payment status and version; it never includes owner identifiers, addresses or user-authored instructions.
- Subscriptions, verified callback cache and deliveries are in PostgreSQL. The subscription ID is derived from canonical owner, event, filters and normalized callback URL. Secret storage uses AES-256-GCM with subscription ID as authenticated context and an external 32-byte key. Persist that key separately from the database and preserve it for recovery; this prototype does not implement master-key rotation or a secret manager.
- Callback challenges are random, signed, checked with constant-time byte comparison and expire after ten seconds. Successful verification is cached for five minutes per owner, URL and signing key. Rotated signing keys are reverified, then old and new signatures overlap for five minutes.
- Default TTL is 24 hours, capped at seven days. A request for no expiration receives the finite default instead. Subscription refresh is idempotent. Only `cursor: null` is supported: durable queued deliveries survive restarts, but this is not protocol history replay, and events during an expired subscription are not recovered.
- The default HTTPS transport validates DNS on every connection, rejects every DNS answer set containing a non-public address, pins the connection to a validated IP, retains the original TLS hostname, disables redirects and connection reuse, and caps request/response bytes and elapsed time. Port 443 only is an intentional additional restriction. Tests inject a transport; there is no environment setting that permits private or HTTP callbacks in deployment.
- Each dispatch checks current order authorization and expiry. The platform's authorization callback must also check current account eligibility. A persisted principal is an identifier for reauthorization, not independent evidence that the account remains connected. Full production OAuth identity and grant lifecycle remains outside this synthetic module.
- Dispatch sends one event per call, using PostgreSQL locks to coordinate workers. Five attempts maximum use exponential delays. HTTP 410 deactivates the subscription; 413 and other non-transient 4xx terminate the delivery. 408, 429, 5xx and network failures retry. Event IDs and serialized payload bytes are stable across retries; signatures use the current attempt time. Delivery is at-least-once: an acknowledgement followed by a database failure can lead to a duplicate. Consumers must deduplicate and tolerate ordering differences.
- Cancellation is serialized with a delivery already in progress; unsubscribe may wait for its bounded HTTPS request to finish. No subsequent delivery starts while a subscription is inactive. Unsubscribe atomically marks existing pending/retry deliveries cancelled; explicitly recreating the subscription does not resurrect those deliveries.
- `revokeAll(principalId)` is a trusted internal platform hook, not an MCP operation. It disables all current subscriptions for that owner, marks pending/retry deliveries revoked, and clears only that owner's callback-verification cache in a transaction. It sends no callback and returns no subscription counts or details. The synthetic OAuth revocation route resolves the owner from the token before deleting it and invokes this hook: revoking one valid customer token conservatively stops **all** that customer's current subscriptions, without affecting other owners. The platform remains responsible for token deletion and authentication; this hook does not invalidate other sessions or prohibit a subsequently authorized new subscription.
- A production implementation still needs per-account subscription/delivery quotas, a retention and dead-letter policy, metrics/alerts, encryption-key rotation, and live ChatGPT acceptance. The platform owns polling, scheduling, rate limits and tenant outbox cursors; this module starts no timers.

Run `node --test events.test.mjs` for local transport/security tests. Set `TEST_DATABASE_URL` to the disposable prototype platform database to additionally exercise actual PostgreSQL restart persistence, encryption, refresh, ownership, expiry, retries, rotation and concurrency. The integration test creates and removes only its own random schema. Without that variable, it explicitly reports the database suite as skipped.
