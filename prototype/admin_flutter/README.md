# نموذج إدارة المطعم بـFlutter

تطبيق إدارة تجريبي مستقل داخل `prototype/`، يبدأ بويندوز. يستهلك [عقد النموذج](../CONTRACT.md) ولا يتصل بقاعدة المطعم الحالية أو واتساب أو بوابة دفع حقيقية. شاشة عربية RTL تعرض تحذيرًا دائمًا بأن البيانات والهويات والدفع اصطناعية.

## التشغيل المحلي على Windows

تحتاج Flutter stable وVisual Studio مع حمل **Desktop development with C++**، وفق [دليل Flutter الرسمي لويندوز](https://docs.flutter.dev/platform-integration/windows/setup). المسار `windows/` مولّد بأداة Flutter الرسمية، وليس إثباتًا أن بناء Windows جُرّب.

1. شغّل خدمات النموذج المحلية كما يشرح دليل `prototype/`. يجب أن يرى Windows عنوان المنصة `http://127.0.0.1:18787`؛ لا تعرض منفذ هويات التطوير للعامة. مع Docker داخل WSL تحقق من وصول loopback من Windows دون تغيير الحماية إلى عنوان عام.
2. من هذا المجلد:

```powershell
flutter doctor -v
flutter pub get
flutter run -d windows --dart-define=PROTOTYPE_API_BASE_URL=http://127.0.0.1:18787
```

يجب أن يطابق العنوان `PUBLIC_BASE_URL` في المنصة بالضبط، بما فيه الفرق بين `localhost` و`127.0.0.1`. يرسل التطبيق `Origin` مطابقًا لجلسة التطوير. لا يقبل التطبيق عنوان خادم عام أو IP من الشبكة المحلية؛ هذا قيد مقصود لأن اختيار الهوية غير موثق وليس تسجيل دخول إنتاجيًا.

اختر `merchant-a` أو `merchant-b`. تعرض كل هوية مطعمها فقط. إن لم توجد طلبات، أنشئ طلبًا اصطناعيًا من مسار العميل المحلي ونفّذ محاكاة الدفع فيه؛ الإدارة لا توفر زر تحصيل ولا محاكاة دفع. ينتقل الطلب المدفوع اصطناعيًا: مقبول ← قيد التحضير ← جاهز ← مكتمل.

## السلوك وحدوده

- رمز bearer قصير العمر موجود في الذاكرة فقط؛ لا كلمات مرور أو مفاتيح خدمة أو DB داخل التطبيق. زر «مسح الجلسة المحلية» يمسح الذاكرة والطلبات، ولا يدعي إبطالًا خادميًا غير موجود في العقد.
- كل كتابة ترسل `expectedVersion` وتنتظر الخادم قبل تحديث الشاشة. فشل اتصال أو تعارض يوقف الكتابات حتى تحديث ناجح. لا إعادة آلية لطلب تغيير حالة بعد نتيجة مبهمة.
- تحديث كل 8 ثوان أثناء نشاط التطبيق، مع منع الطلبات المتداخلة وإيقاف المؤقت عند الخروج أو تعليق التطبيق. الرجوع للمقدمة يجلب الحالة قبل فتح الكتابة. الشبكة قد تنقطع بين فحصين؛ لا تثبت الواجهة نجاح عملية ما لم يؤكده الخادم.
- الطلبات المعروضة قبل انقطاع الشبكة موسومة بوقت آخر تحديث ومؤشر توقف. إنهاء الجلسة يمنع نتائج طلب HTTP قديم من إعادة بيانات مطعم سابق للشاشة.
- حدود HTTP: مهلة اتصال، مهلة عملية، حجم استجابة محدود، وعدم اتباع redirects أو عرض أجسام أخطاء غير موثوقة. يفحص العميل هوية المطعم في النتائج؛ الحماية الأساسية للأدوار والملكية تبقى في الخادم.
- لا طباعة، ولا صوت/تنبيه خلفية، ولا إدارة منيو أو مخزون أو استرداد، ولا تخزين بيانات عملاء، ولا OAuth إنتاجي في هذا النموذج. لم يبدأ Android أو iOS؛ استعمال `dart:io` هنا يستهدف التطبيقات الأصلية ولا يجهّز نسخة ويب.

## التحقق

```powershell
flutter analyze
flutter test
```

الاختبارات تغطي حجب الكتابة بعد الفشل، تعارض النسخة ومنع الإعادة الآلية، منع الانتقال لطلب غير مدفوع، تبديل المطاعم ومسح الردود المتأخرة، انتهاء الجلسة، تنظيف مؤقت المتابعة، RTL والتخطيط الضيق، وعقد HTTP حقيقي على loopback بـخادم اختبار. اختبارات الواجهة على محرك اختبار Linux لا تعني قبول Windows فعليًا ولا قبول خدمات المنصة كاملة.

أدوات إعداد هذه النسخة: Flutter **3.47.5** وDart **3.13.4** من فرع stable الرسمي عند commit `6a19cca56475dbfba1478ee68d7bd0c2ef891da1`. لا تتطلب إعادة تثبيت SDK داخل المستودع؛ `pubspec.lock` يثبت الحزم. لتوليد scaffold جديد عند الحاجة، استخدم في مجلد فارغ `flutter create --platforms=windows --project-name restaurant_admin_prototype --org dev.synthetic` ثم انقل ملفات التطبيق؛ لا تستبدل تخصيصات runner القائمة دون مراجعة.

نتيجة التحقق في 30 سبتمبر 2026 على Linux: `flutter analyze --no-pub` بلا ملاحظات، و`flutter test --no-pub --reporter expanded` ناجح **12/12**. خادم اختبار HTTP محلي اصطناعي؛ هذه النتيجة لا تثبت تشغيل التطبيق مع منصة Docker الكاملة أو تسجيل دخول إنتاجي. فشل التجميع الأول بسبب اسم ثابت ترويسة HTTP وصُحح قبل النتيجة النهائية.

القبول المتبقي: تشغيل على Windows فعلي واختبار العربية والإدخال وحالات الشبكة ونوم الجهاز وإغلاق النافذة، ثم تصميم تسجيل دخول إنتاجي وأدوار وتكافؤ وظائف الإدارة والطباعة وإشعارات التشغيل. لاحقًا يلزم توقيع حزمة Windows وتحديثاتها؛ لم يُنشأ أو يُوقّع ملف EXE في بيئة Linux هذه.

## نمط النواة الحقيقية — 5 أكتوبر 2026

الوصف السابق يخص نمط النموذج الاصطناعي الذي يبقى مستقلًا عند غياب
`CORE_API_BASE_URL`. يوجد الآن نمط إدارة حقيقي منفصل، يستعمل جسر الموظفين
في `prototype/platform/NATIVE-STAFF-AUTH.md` ولا يتصل بقاعدة البيانات مباشرة.

```powershell
$env:CI='true'
$env:BOT='true'
flutter --suppress-analytics pub get --enforce-lockfile
flutter --suppress-analytics run -d windows --dart-define=CORE_API_BASE_URL=https://YOUR-APPROVED-CONTROL-HOST
```

استبدل العنوان بأصل منصة HTTPS المشغلة فعليًا، دون مسار أو مفاتيح في العنوان.
إعداد خاطئ يُظهر خطأ؛ لا يتحول التطبيق تلقائيًا إلى هويات التجربة. يلزم تفعيل
`CORE_NATIVE_STAFF_ENABLED=true` على منصة الاختبار، وتوفير هوية OIDC موثقة
وعضوية موظف فعالة. لا تُضمّن أي سر خدمة أو مزود دفع في بناء Flutter.

- متصفح النظام + PKCE S256 وحالة/مصدر استجابة مربوطان، callback على
  `127.0.0.1` بمنفذ عشوائي، مهلة دخول 5 دقائق وزر إلغاء.
- access token في الذاكرة فقط، refresh token في مخزن نظام التشغيل الآمن
  بمفتاح خاص بأصل المنصة. لا SharedPreferences ولا ملف نصي بديل عند الفشل.
  عمر الربط الخادمي الأقصى 8 ساعات، تدوير refresh دون إعادة مبهمة.
- خروج يمسح ذاكرة التطبيق ومفتاحه فقط ويحاول الإبطال الخادمي. تظهر رسالة
  منفصلة إذا لم يتأكد المسح أو الإبطال. الإغلاق العادي يحتفظ بـrefresh الآمن
  لاستئناف الجلسة المسموحة؛ صفحة `/native/sessions` تبطل جلسات الأجهزة.
- اختيار صريح عند تعدد المطاعم؛ تبديل المطعم والخروج يغلقان نتائج الطلبات
  المتأخرة. إزالة العضوية/الصلاحية تمسح الطلبات الخاصة.
- آخر 100 طلب، تفاصيل العناصر والإضافات والملاحظات والطاولة، انتقال الحالة
  الإيجابي وتسجيل استلام النقد وفق الصلاحيات. كل إجراء يحتاج تأكيدًا ونسخة
  حديثة، ويرسل رقم النسخة الأصلي. لا تحصيل بوابة دفع من التطبيق ولا إعادة
  كتابة تلقائية بعد نتيجة غير مؤكدة.
- تحديث دوري كل 10 ثوان في المقدمة، قراءات متسلسلة، توقف الكتابة بعد فشل
  الشبكة أو قدم البيانات أو تعليق التطبيق. هذا ليس حل scale نهائيًا؛ يلزم
  اختبار حمل وضبط حد المعدل خلف reverse proxy قبل تشغيل عدد كبير من الأجهزة.
- لا تُخزن الطلبات أو تفاصيلها على القرص. لا تحويلات HTTP ولا تجاوز TLS،
  وحدود مهلة/حجم، وربط tenant/order في الاستجابات.
